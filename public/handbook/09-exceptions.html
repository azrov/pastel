#9. When things go wrong

Files are missing, users type letters where numbers belong, networks drop. A good program expects this and handles it in one place, instead of checking for errors after every line. Object Pascal does it with exceptions.

#An exception stops everything — unless it is caught

When something goes wrong, code raises an exception: an object that describes the problem. From that point, nothing more of the current routine runs; the exception travels up through the routines that called it, until some code catches it. If nobody does, the program stops and prints the message.

program Catching;

{$mode objfpc}{$H+}

uses
  SysUtils;

var
  N: Integer;
begin
  try
    N := StrToInt('twelve');
    WriteLn('This line never runs: ', N);
  except
    on E: EConvertError do
      WriteLn('Not a number: ', E.Message);
  end;
  WriteLn('The program goes on.');
end.

Not a number: "twelve" is an invalid integer
The program goes on.

try … except runs the try part; if an exception is raised inside it (also deep inside a routine it calls), the except part runs. on E: EConvertError do catches only exceptions of that class (and its children), and E is the exception object — E.Message its text. The exception object is freed by itself after the handler.

#Several kinds

program Kinds;

{$mode objfpc}{$H+}

uses
  SysUtils;

procedure Run(const S: string);
var
  N, Q: Integer;
begin
  try
    N := StrToInt(S);
    Q := 100 div N;
    WriteLn('100 / ', N, ' = ', Q);
  except
    on E: EConvertError do
      WriteLn('"', S, '" is not a number.');
    on E: EDivByZero do
      WriteLn('Cannot divide by zero.');
    on E: Exception do
      WriteLn('Something else: ', E.ClassName, ': ', E.Message);
  end;
end;

begin
  Run('4');
  Run('x');
  Run('0');
end.

100 / 4 = 25
"x" is not a number.
Cannot divide by zero.

The first on that fits is used, so put the specific ones first and Exception — the parent of all exceptions — last.

Why compute Q before the WriteLn, and not write 100 div N inside it? WriteLn writes its parts one after the other: with N = 0 it would already have written 100 / 0 = when the division fails. Do the work first, then write the result.

#Raising your own

raise throws an exception. Make a class for the kinds of problems your code has; it can be caught apart from everything else:

program Raising;

{$mode objfpc}{$H+}

uses
  SysUtils;

type
  EBudgetError = class(Exception);

procedure Spend(var Budget: Currency; Amount: Currency);
begin
  if Amount <= 0 then
    raise EBudgetError.Create('an amount is more than zero');
  if Amount > Budget then
    raise EBudgetError.CreateFmt('%s is more than the %s left', [CurrToStr(Amount), CurrToStr(Budget)]);
  Budget := Budget - Amount;
end;

var
  Budget: Currency;
begin
  Budget := 100;
  try
    Spend(Budget, 30);
    Spend(Budget, 80);
    Spend(Budget, 10);
  except
    on E: EBudgetError do
      WriteLn('Refused: ', E.Message);
  end;
  WriteLn('Left: ', CurrToStr(Budget));
end.

Refused: 80 is more than the 70 left
Left: 70

Create takes the message; CreateFmt builds it like Format. The third Spend never runs: the exception left the try block at the second.

#finally and except together

finally (chapter 8) cleans up whatever happens; except handles a problem. They do different jobs, and often appear together — finally inside, except outside:

program Together;

{$mode objfpc}{$H+}

uses
  Classes, SysUtils;

procedure Load(const FileName: string);
var
  Lines: TStringList;
begin
  Lines := TStringList.Create;
  try
    Lines.LoadFromFile(FileName);     // raises when the file is not there
    WriteLn(Lines.Count, ' lines');
  finally
    Lines.Free;                       // runs in both cases
    WriteLn('(freed)');
  end;
end;

begin
  try
    Load('/no/such/file.txt');
  except
    on E: Exception do
      WriteLn('Could not load: ', E.ClassName);
  end;
end.

(freed)
Could not load: EFOpenError

The finally ran first (on the way out of Load), then the except that caught it.

#Passing it on

An except block can do something and let the exception go on with a bare raise;. This is how a routine undoes its half-done work:

Result := TEntry.Create;
try
  Result.Amount := AnAmount;      // may raise
except
  Result.Free;                    // not handed out: freed here
  raise;                          // and the caller still learns what went wrong
end;

That is the start of Pocket's TEntryList.AddEntry (chapter 10).

#When to use them

  • Exceptions are for the unexpected: a file that should be there is not, a value that cannot be right. They carry the problem to the place that can deal with it — often the top of the program, which tells the user.
  • For expected cases, a result is simpler. A user typing a wrong number is normal: TryStrToInt and Pocket's TryParseMoney answer False instead of raising. Use a Try… function where a failure is part of the normal flow.
  • Catch what you can handle. on E: Exception do around everything hides bugs. Catch the kinds you expect, where you know what to do.
  • Never leave an except empty. An error that is swallowed silently is the hardest bug to find.

In a Pastel app, an exception that no code catches in an event handler (a button's OnClick) does not crash the app: Pastel shows its message to the user, writes it to the console, and the app goes on. Application.OnException lets you handle them all in one place.

#In Pocket

TEntry's Amount refuses negative values with EArgumentException (chapter 8). The command line will catch the errors the user can fix — a wrong amount, a missing file — and show them in one line; anything else stops the program with its message, because it is a bug to fix. Here is the idea in small:

program PocketErrors;

{$mode objfpc}{$H+}

uses
  SysUtils, PocketMoney;

type
  EInputError = class(Exception);

function AmountFrom(const S: string): Currency;
begin
  if not TryParseMoney(S, Result) then
    raise EInputError.CreateFmt('"%s" is not an amount like 12.50', [S]);
  if Result <= 0 then
    raise EInputError.Create('the amount is more than zero');
end;

procedure Add(const S: string);
var
  Amount: Currency;
begin
  try
    Amount := AmountFrom(S);
    WriteLn('Added ', FormatMoney(Amount));
  except
    on E: EInputError do
      WriteLn('error: ', E.Message);
  end;
end;

begin
  Add('12.50');
  Add('lunch');
  Add('0');
end.

Added 12.50
error: "lunch" is not an amount like 12.50
error: the amount is more than zero

#Exercises

  1. Read a number with ReadLn and StrToInt; catch EConvertError and ask again until it works.
  2. Make EAgeError and a procedure CheckAge(Age: Integer) that raises it outside 0..150. Catch it in the program.
  3. What does StrToInt('99999999999') raise? Find out by catching Exception and printing E.ClassName.
  4. ★ Write function SafeDivide(A, B: Integer; out Q: Integer): Boolean — the Try… style — and compare a program that uses it with one that catches EDivByZero. Which reads better?
