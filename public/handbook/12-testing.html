#12. Testing

You changed TryParseMoney to accept a new way of writing amounts. Does 12,50 still work? And -7? Checking by hand after every change is slow, and one day you forget. A test is a small piece of code that checks a piece of your program and says pass or fail — and the computer runs hundreds of them in a second, every time.

#A test suite

Tests live in the tests/ folder of a project. A test unit has a class built on TTestSuite; every published method is one test:

unit Money_Test;

{$mode objfpc}{$H+}

interface

uses
  Pastel.Testing, PocketMoney;

type
  TMoneyTests = class(TTestSuite)
  published
    procedure WritesCommasAndCents;
    procedure ReadsWhatPeopleType;
    procedure RefusesWords;
  end;

implementation

procedure TMoneyTests.WritesCommasAndCents;
begin
  AssertEquals('0.00', FormatMoney(0));
  AssertEquals('1,234.50', FormatMoney(1234.5));
  AssertEquals('-45.05', FormatMoney(-45.05));
end;

procedure TMoneyTests.ReadsWhatPeopleType;
var
  A: Currency;
begin
  AssertTrue(TryParseMoney('12,50', A));
  AssertTrue(A = 12.5, 'a comma before the cents');
  AssertTrue(TryParseMoney('1.234,50', A));
  AssertTrue(A = 1234.5, 'dots between thousands');
end;

procedure TMoneyTests.RefusesWords;
var
  A: Currency;
begin
  AssertFalse(TryParseMoney('lunch', A));
  AssertFalse(TryParseMoney('', A));
end;

initialization
  RegisterTests(TMoneyTests);

end.

Run them:

pastel test

Money
  PASS writes commas and cents (0 ms)
  PASS reads what people type (0 ms)
  PASS refuses words (0 ms)

Tests: 3 passed, 3 total (1 ms)

Pastel finds the test units in tests/, builds them into a test program and runs it. The method names become the test names — so name them as sentences about what should be true.

#Asserts
AssertEquals(Expected, Actual) for strings, whole numbers, Double (with a tolerance), Boolean
AssertTrue(Condition), AssertFalse(Condition) anything else
AssertContains(Part, Text), AssertStartsWith(Start, Text) parts of text
AssertNil(X), AssertNotNil(X) references
AssertRaises(EClass, @Proc) that a procedure raises an exception
Fail(Message) fail here (a line that must not be reached)
Skip(Reason) not here (a database server that is not running)

Every assert takes a last parameter, a message that is shown when it fails — use it when the line alone would not say what went wrong. The expected value comes first: a failure then reads "expected 1,234.50 but got 1234.50".

A failing test shows where:

  FAIL writes commas and cents
       expected "1,234.50" but got "1234.50"
       at tests/money_test.pas:26

#Testing exceptions

Two ways: AssertRaises, or a try with Fail in it — this one also lets you look at the message:

procedure TPocketTests.AnAmountIsNeverNegative;
var
  L: TEntryList;
begin
  L := TEntryList.Create;
  try
    try
      L.AddEntry(Date, ekExpense, 'Food', -5);
      Fail('a negative amount was taken');
    except
      on E: EArgumentException do
        AssertContains('never negative', E.Message);
    end;
    AssertEquals(0, L.Count, 'not added');
  finally
    L.Free;
  end;
end;

#SetUp and TearDown

When every test of a suite needs the same start — a list with sample entries, an empty folder — override SetUp (runs before each test) and TearDown (after each, also when it failed):

type
  TStoreTests = class(TTestSuite)
  private
    FDir: string;
  public
    procedure SetUp; override;
    procedure TearDown; override;
  published
    procedure SavesAndLoads;
  end;

procedure TStoreTests.SetUp;
begin
  FDir := MakeTempDir('pocket');      // a new empty folder for each test
end;

procedure TStoreTests.TearDown;
begin
  DeleteDir(FDir);
end;

Tests must not depend on each other or on their order: each one starts clean.

#Choosing and watching

pastel test Money            # only the tests whose suite or name contains "Money"
pastel test --watch          # run them again at every save

In VS Code the Testing view lists every test with a ▶ to run it, and the failing line is marked in the editor.

#What to test

Test the parts with rules: parsing, calculations, decisions — Pocket's money, its totals, its store. Each test checks one thing and its name says which. When you find a bug, first write a test that fails because of it, then fix the code: the bug can never come back unnoticed.

#A library: code for more than one program

Pocket will have two programs: the command line (chapter 13) and the app (part 2). Both need the same entries, money and reports. Copying the units would mean fixing every bug twice. Instead, they go into a library project that both programs use:

pastel new lib pocket-core

pocket-core/
├── pastel.toml        type = "lib": units for other projects, no program of its own
├── src/               PocketMoney, PocketEntries, PocketReports...
└── tests/             their tests

Move the units of chapters 7–11 into pocket-core/src/, and the tests into pocket-core/tests/. Then each program names the library in its pastel.toml:

[dependencies]
pocket-core = { path = "../pocket-core" }

Now uses PocketMoney finds the library's unit, and pastel build compiles it with the program. A fix in pocket-core reaches both programs at their next build. Libraries can also come from git or from Pastel's package registry (packages.md).

The book's projects sit side by side:

pocket-core/      the library: chapters 7–13
pocket-cli/       the command line: chapter 13
pocket-app/       the app: part 2

All of Pocket's tests are in examples/pocket-core/tests/pocket_test.pas: money, the list, the reports, both stores and the bank import.
